# Chicago Pizza: запуск с нуля на Aeza через Dokploy

Подробная инструкция для Windows на вашем компьютере и нового Ubuntu VPS. Выполняйте разделы по порядку. Все компоненты приложения работают на одном VPS; образы собираются в GitHub Actions, а не на маленьком сервере. Покупку и регистрацию внешних услуг выполняете вы. Названия кнопок в кабинетах могут немного изменяться: ориентируйтесь также на назначение поля.

Основной домен ниже — **пример** `chicago-pizza.ru`, его доступность не проверена. Если купите другое имя, заменяйте пример везде. Панель будет на `panel.ВАШ_ДОМЕН`; поддомен отдельно покупать не нужно.

## 0. Подготовить заметку и понять обозначения

Сохраните в менеджере паролей: аккаунты Aeza/GitHub, IPv4 VPS, выбранный домен, email владельца, доступ к SMTP, отдельные пароли панели и администратора пиццерии. Администратор Dokploy управляет сервером; администратор сайта управляет пиццерией. Это разные аккаунты.

В командах:

- `IP_ВАШЕГО_VPS` — IPv4 из карточки сервера Aeza.
- `ВАШ_ДОМЕН` — купленное имя без `https://`.
- `ПОЛНЫЙ_SHA` — 40 символов конкретного коммита GitHub, объяснение ниже.
- `ИМЯ_КОНТЕЙНЕРА` — реальное имя из `docker ps`, не название наугад.
- Блок `powershell` выполняется **на вашем Windows-компьютере**.
- Блок `bash` выполняется **внутри SSH на VPS**.

Копируйте только команды, без строки приглашения `PS C:\>` или `root@...#`. Если получена ошибка, остановитесь на этом шаге. Секреты, `.env`, приватные SSH-ключи и дампы базы не публикуются в GitHub/скриншотах.

## 1. Зарегистрироваться в Aeza и купить VPS

1. Откройте [aeza.ru](https://aeza.ru/) → личный кабинет. Создайте аккаунт со своим доступным email и подтвердите его.
2. Включите двухфакторную защиту, сохраните резервные коды. Пополните баланс через кабинет. Перед оплатой проверьте услугу, период и итоговую сумму.
3. Выберите **виртуальный сервер VPS/VDS**. Не обычный веб-хостинг, не VPN и не сервер только для хранения файлов.
4. Ищите самый дешёвый подходящий тариф: **2 vCPU или больше, 4 ГБ RAM или больше, 40+ ГБ SSD/NVMe, публичный IPv4, x86_64/amd64**. 8 ГБ дадут запас, но не обязательны для пробного запуска. Фиксированную цену эта инструкция не обещает.
5. Не выбирайте 1–2 ГБ для всего приложения. Помимо Dokploy работают PostgreSQL, RabbitMQ, два Redis, шесть серверных процессов и Next.js. 4 ГБ — предварительная оценка; перед открытием сайта надо измерить потребление. Сам Dokploy указывает минимум 2 ГБ/30 ГБ, это не минимум всего проекта.
6. Выберите доступную локацию с подходящей задержкой до Махачкалы. До оплаты уточните у поддержки: «Нужны Docker/Dokploy, доступ к GitHub/GHCR и исходящий SMTP 465/587. Есть ли ограничения на этом VPS?»
7. По вашему пожеланию об актуальной Ubuntu — **Ubuntu Server 26.04 LTS**. Docker её поддерживает; список явно проверенных ОС Dokploy пока включает 24.04 LTS, а не 26.04. Поэтому установку на 26.04 сначала проверяют на новом пустом VPS. 24.04 LTS — запасной вариант, если возникнут подтверждённые проблемы совместимости.
8. Если при покупке можно добавить SSH-ключ, сначала выполните раздел 3 и вставьте публичный `.pub`. Если VPS уже создаётся — сохраните root-пароль, ключ можно добавить после первого входа.
9. Для постоянного сайта выберите подходящую месячную оплату и автопродление. Прочитайте правила удаления услуги при нехватке средств; включите уведомления о балансе.
10. Дождитесь работающего статуса VPS. Откройте карточку и запишите IPv4, пользователя (обычно `root`) и способ входа.

Источники: [Aeza VPS](https://aeza.ru/virtual-servers), [требования Dokploy](https://docs.dokploy.com/docs/core/installation), [Ubuntu 26.04](https://documentation.ubuntu.com/release-notes/26.04/).

## 2. Купить домен и настроить DNS

1. Откройте [домены Aeza](https://aeza.ru/domains). Введите желаемое имя и нажмите проверку доступности. Если занято — выберите другое.
2. Проверьте срок, цену регистрации и продления. Домен оплачивается отдельно от VPS.
3. Внесите настоящие данные владельца, которые требует регистратор. Оплатите и дождитесь активации.
4. В кабинете откройте «Мои домены» → домен → DNS. При необходимости включите DNS Aeza и проверьте NS по данным кабинета; официальная инструкция приводит `a.aeza-dns.net` и `b.aeza-dns.net`.
5. Создайте записи:

| Тип | Имя/Host | Значение | TTL |
| --- | --- | --- | --- |
| A | `@` или пустое имя корня | IPv4 VPS | Авто или 300 |
| A | `panel` | Тот же IPv4 | Авто или 300 |

6. Если интерфейс требует полное имя, используйте основной домен и `panel.ВАШ_ДОМЕН`. Не создайте случайно `panel.домен.домен`.
7. A-запись содержит только IP. Не пишите туда `https://`, путь или адрес страницы. Уберите парковочные A-записи на чужой IP. AAAA пока не добавляйте, если IPv6 сайта не настроен.
8. Сохраните. Смена NS по инструкции Aeza может занимать до 24–72 часов; отдельная A-запись часто обновляется быстрее.
9. В Windows: «Пуск» → PowerShell. Подставьте ваш домен:

```powershell
Resolve-DnsName chicago-pizza.ru -Type A
Resolve-DnsName panel.chicago-pizza.ru -Type A
```

В ответах должен появиться IPv4 VPS. Если имени нет или IP старый, проверьте DNS и подождите. Для первого запуска `www` не нужен; его подключение позднее требует и DNS, и отдельной настройки домена/редиректа в Dokploy.

Источники: [регистрация](https://wiki.aeza.net/ru/domains/registration/), [подключение к серверу](https://wiki.aeza.net/ru/domains/link-to-server/), [NS Aeza](https://wiki.aeza.net/ru/domains/transfer-dns-manage/).

## 3. Подготовить SSH на Windows

SSH позволяет выполнять команды на VPS. Все команды этого раздела сначала вводятся в PowerShell компьютера.

1. Проверьте `ssh -V`. Если команды нет, установите «Клиент OpenSSH» через дополнительные компоненты Windows и заново откройте PowerShell.
2. Создайте отдельный ключ:

```powershell
ssh-keygen -t ed25519 -f "$env:USERPROFILE\.ssh\chicago_aeza" -C "chicago-pizza-vps"
```

При вопросе overwrite существующего файла ответьте `n` и сначала выясните, чей это ключ. Для нового ключа задайте пароль и сохраните его. Ввод пароля может не показывать символы — это нормально.

3. `chicago_aeza` — секретный файл, `chicago_aeza.pub` — публичный. Скопируйте только публичный:

```powershell
Get-Content "$env:USERPROFILE\.ssh\chicago_aeza.pub" | Set-Clipboard
```

Вставьте строку в настройку SSH-ключа Aeza при создании VPS. Файл без `.pub` не загружайте.

4. Если сервер создан с паролем, первый вход:

```powershell
ssh root@IP_ВАШЕГО_VPS
```

Первый fingerprint сверяют с данными/консолью нового VPS, затем подтверждают `yes`. При изменении ключа знакомого сервера сначала выясните причину, не удаляйте проверку автоматически. Введите root-пароль; ни букв, ни звёздочек может не быть.

5. Если ключ ещё не установлен, внутри VPS:

```bash
mkdir -p /root/.ssh
chmod 700 /root/.ssh
nano /root/.ssh/authorized_keys
```

Вставьте публичную строку `ssh-ed25519 ...`. В `nano`: Ctrl+O → Enter сохраняет, Ctrl+X выходит. Затем:

```bash
chmod 600 /root/.ssh/authorized_keys
```

6. Не закрывая первый вход, откройте второй PowerShell:

```powershell
ssh -i "$env:USERPROFILE\.ssh\chicago_aeza" root@IP_ВАШЕГО_VPS
```

Если вход работает, ключ настроен. До этой проверки не выключайте парольную авторизацию и не закрывайте первый сеанс. `exit` закрывает SSH, а не выключает VPS.

Источник: [SSH Aeza](https://wiki.aeza.ru/guides/connect-ssh-sftp/).

## 4. Подготовить новый Ubuntu VPS

Далее блоки `bash` — внутри SSH. Инструкция рассчитана на новый VPS, не на сервер с уже работающими чужими сайтами.

1. Проверьте ОС и ресурсы:

```bash
cat /etc/os-release
free -h
df -h /
```

2. Обновите систему и установите утилиты:

```bash
apt update
apt upgrade -y
apt install -y curl ca-certificates git nano openssl ufw dnsutils netcat-openbsd
timedatectl set-timezone Europe/Moscow
```

Если требуется reboot, выполните `reboot`, подождите и подключитесь снова. Разрыв SSH при перезагрузке ожидаем.

3. На 4 ГБ можно добавить swap 2 ГБ. Сначала проверьте:

```bash
swapon --show
test -e /swapfile && echo '/swapfile уже существует'
```

Только если swap отсутствует и файл `/swapfile` не существует:

```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile
printf '/swapfile none swap sw 0 0\n' >> /etc/fstab
free -h
```

Не повторяйте создание файла и добавление строки. Swap помогает пережить пик, но не заменяет нужную RAM.

4. Проверьте `ss -lntp`: порты 80, 443, 3000 должны быть свободны. Не устанавливайте отдельный системный Nginx/Apache — публичные 80/443 займёт Traefik Dokploy.
5. Узнайте публичный IP **вашего компьютера**, не VPS. Подставьте его:

```bash
ufw default deny incoming
ufw default allow outgoing
ufw allow from IP_ВАШЕГО_КОМПЬЮТЕРА to any port 22 proto tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
ufw status
```

Сразу проверьте второй SSH-вход. При смене домашнего IP правила обновляют через консоль Aeza или заранее организуют VPN-доступ. Консоль Aeza должна оставаться способом восстановления доступа.

Не открывайте БД, Redis, RabbitMQ management и Swarm-порты для всех. Для опубликованных Docker-портов одного UFW недостаточно: порт панели отдельно ограничивается ниже.

## 5. Установить Dokploy и создать владельца

1. До установки по возможности ограничьте порт 3000 вашим IP на внешнем firewall/ACL Aeza. Если такой возможности в кабинете нет, уточните у поддержки. После установки владельца мы снимем публикацию порта полностью.
2. На VPS скачайте официальный скрипт и просмотрите:

```bash
curl -fsSL https://dokploy.com/install.sh -o /tmp/dokploy-install.sh
less /tmp/dokploy-install.sh
```

Выход из `less` — `q`. Затем от root:

```bash
sh /tmp/dokploy-install.sh
```

Дождитесь завершения. Не повторяйте установку при неизвестной ошибке; сохраните её текст. Проверьте:

```bash
docker version
docker compose version
docker service ls
docker ps
docker network inspect dokploy-network --format '{{json .IPAM.Config}}'
```

3. Если нет внешнего ACL, для стандартного Docker с iptables ограничьте перенаправленный порт панели. Сначала убедитесь, что существует цепочка:

```bash
iptables -S DOCKER-USER
```

Если она существует, добавьте правило с **вашим** IP:

```bash
iptables -I DOCKER-USER -p tcp --dport 3000 ! -s IP_ВАШЕГО_КОМПЬЮТЕРА -j DROP
```

Если цепочки нет, используется иной firewall backend — не копируйте случайные правила; примените внешний ACL/официальную инструкцию Docker для вашего backend. Для VPS с публичным IPv6 также нужна соответствующая IPv6-защита. Не оставляйте открытую страницу создания владельца без контроля.

4. Удобно открыть панель через SSH-туннель. В новом PowerShell компьютера:

```powershell
ssh -i "$env:USERPROFILE\.ssh\chicago_aeza" -L 13000:127.0.0.1:3000 root@IP_ВАШЕГО_VPS
```

Оставьте окно открытым. Откройте в браузере **`http://127.0.0.1:13000`**. Это Dokploy VPS через SSH, не локальная пиццерия.

5. Создайте владельца Dokploy: ваш email и отдельный длинный пароль. Сохраните данные. Не откладывайте создание владельца после установки.

Источник: [Dokploy installation](https://docs.dokploy.com/docs/core/installation), [Docker firewall](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

## 6. Сделать HTTPS панели

1. В настройках Dokploy/сервера найдите поле домена панели (`Server Domain`/`Domain`). Укажите `panel.ВАШ_ДОМЕН` в формате подсказки поля. Если представлены отдельные переключатели — HTTPS и Let's Encrypt.
2. Сохраните и откройте в новом окне `https://panel.ВАШ_ДОМЕН`. DNS уже должен указывать на VPS. Проверьте сертификат и вход.
3. В аккаунте Dokploy включите 2FA и сохраните резервные коды.
4. **Только после успешного входа по HTTPS**, на VPS:

```bash
docker service update --publish-rm "published=3000,target=3000,mode=host" dokploy
```

5. Проверьте, что HTTPS-панель продолжает работать. Закройте туннель. Прямой `IP:3000` теперь не нужен. При восстановлении используйте SSH/консоль, не открывайте все порты наугад.

## 7. Настроить настоящую почту

Регистрация покупателя требует письма с кодом. Зелёный SMTP-контейнер без реальной доставки писем не означает работающую регистрацию. MailHog в production отсутствует.

1. Выберите SMTP/почтовый сервис для бизнеса либо используйте существующий. Он должен позволять отправку от вашего домена через стандартный SMTP.
2. Добавьте домен у провайдера и подтвердите владение TXT-записью, которую он покажет. Внесите её в DNS Aeza.
3. Если нужны входящие письма, добавьте MX по его инструкции. Для исходящих настройте SPF/DKIM; ключи берите у своего провайдера. Не создавайте две SPF-записи на одном имени, существующую объединяют.
4. Создайте ящик/разрешённого отправителя, например `no-reply@ВАШ_ДОМЕН`. При 2FA создайте пароль приложения, если так требует провайдер.
5. Запишите SMTP host, порт, TLS, логин, пароль и разрешённый From. Формат:

```dotenv
SMTP_HOST=ХОСТ_ВАШЕГО_SMTP
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=no-reply@ВАШ_ДОМЕН
SMTP_PASSWORD=ПАРОЛЬ_SMTP
MAIL_FROM=Chicago Pizza <no-reply@ВАШ_ДОМЕН>
```

Обычно 465 — `SMTP_SECURE=true`, 587/STARTTLS — `false`; требования вашего провайдера важнее примера. From не может быть произвольным неподтверждённым адресом.

6. На VPS: `nc -vz ХОСТ_SMTP 465` с настоящим host/портом. Это проверяет сеть, не отправку. При timeout выясните ограничения у Aeza/провайдера. Настоящее письмо проверим после запуска.

## 8. Опубликовать образы в GitHub

1. Откройте [репозиторий](https://github.com/IR-Full/chicago-pizza) → Actions → **CI**. Найдите запуск именно последнего коммита `main`, дождитесь зелёного результата.
2. Если красный, откройте упавшую задачу и лог. Не отключайте security/migration-проверки ради Deploy.
3. В Actions выберите **Publish deployment images** → **Run workflow** → Branch **main**.
4. В `site_url` впишите `https://ВАШ_ДОМЕН` **без завершающего слеша**. Это должен быть купленный основной домен сайта, не домен панели.
5. `map_key` — ваш публичный ключ 2GIS, разрешённый для домена. Если его пока нет, оставьте пустым: можно вводить адрес вручную.
6. Нажмите Run workflow, дождитесь успешного окончания. Workflow проверит код/БД и создаст серверный и клиентский образы.
7. Откройте коммит этого запуска, скопируйте полный SHA из 40 символов. Образы:

```text
ghcr.io/ir-full/chicago-pizza-server:ПОЛНЫЙ_SHA
ghcr.io/ir-full/chicago-pizza-client:ПОЛНЫЙ_SHA
```

Оба используют **один** SHA. Сокращённые 7 символов и `latest` не подставляйте. Смена домена требует новой сборки клиента с правильным `site_url`; одной смены env в Dokploy недостаточно.

SMTP/ЮKassa ключи не нужны для сборки: их задают в Dokploy позже. Не передавайте их в build-args/`NEXT_PUBLIC_*`.

## 9. Подключить GitHub и GHCR к Dokploy

Git содержит Compose и конфиги; GHCR — образы. Это разные источники доступа.

1. Dokploy → Git Sources/Providers → GitHub. Авторизуйтесь, установите GitHub App с доступом к **этому репозиторию**, завершите подключение. Если список пуст, проверьте разрешение приложения GitHub.
2. Для публичного репозитория возможен Git source с URL `https://github.com/IR-Full/chicago-pizza.git`; private требует авторизованный источник/ключ.
3. После публикации откройте Packages вашего GitHub: `chicago-pizza-server`, `chicago-pizza-client`.
4. Если хотите публичные образы, в settings обоих packages смените visibility на public. Это открывает их содержимое всем. Публичный Git сам по себе не гарантирует публичность packages.
5. Для private packages создайте GitHub **Personal access token (classic)** с `read:packages`, сроком действия и доступом к этим packages. Write/delete для скачивания не нужны. Для организации отдельно проверяются SSO/политики.
6. Dokploy → Registry → Add:

| Поле | Значение |
| --- | --- |
| Name | `GitHub images` |
| Registry URL | `ghcr.io` |
| Username | `IR-Full` |
| Password/Token | Токен `read:packages` |
| Server | Ваш сервер Dokploy |

7. Сохраните, проверьте подключение. Не вставляйте токен в Git/Compose/имя образа. Следите за сроком действия.

Источник: [GHCR Dokploy](https://docs.dokploy.com/docs/core/registry/ghcr).

## 10. Создать Compose-приложение

1. Dokploy → Create Project, имя `Chicago Pizza`.
2. Внутри → Create Service → **Docker Compose**. Не Application/Nixpacks и не отдельные Database-сервисы.
3. Имя `chicago-pizza`, окружение production, если такое поле есть.
4. Источник — GitHub/Git вашего репозитория, Branch **main**.
5. Compose path — **`docker-compose.dokploy.yml`**, без первого `/`. Build path — корень репозитория, если требуется.
6. Deployment type — **Docker Compose**, не Docker Stack: нужны Compose-условия запуска миграций.
7. Для данной инструкции используйте обычный режим сети с `dokploy-network`. Если включено **Isolated Deployments**, выключите его для первого запуска: файл уже задаёт внутреннюю сеть и подключает к Traefik только nginx. Не смешивайте варианты без проверки Preview Compose.
8. Пока выключите auto-deploy на каждый push: образы будем менять по проверенным SHA.
9. Не нажимайте Deploy до Environment и домена.

Источник: [сети Compose](https://docs.dokploy.com/docs/core/docker-compose/utilities).

## 13. Первый Deploy

1. Нажмите Deploy, откройте Deployments/Logs. Дождитесь скачивания образов; не нажимайте кнопку многократно.
2. PostgreSQL/Redis/RabbitMQ стартуют, затем `migrate` применит миграции, затем серверные процессы. Для `migrate` exited/completed с кодом **0** — нормальное успешное состояние.
3. На VPS проверьте:

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}'
docker compose ls
```

4. В браузере `https://ВАШ_ДОМЕН/health/ready` должен вернуть JSON `ok`. Путь не `/api/health/ready`.
5. Откройте сайт. До seed меню новой БД может быть пустым. Не принимайте реальные заказы, пока не проверены меню и бизнес-настройки.

## 14. Создать меню и администратора пиццерии один раз

Только для **новой пустой базы**. Seed заполняет меню/филиалы и может перезаписать изменения при повторном запуске. Он не переносит вашу локальную БД.

1. На VPS выполните `docker ps --format 'table {{.Names}}\t{{.Image}}'`. Найдите контейнер **orders этого приложения** и подставьте:

```bash
PIZZA_ORDERS='ИМЯ_КОНТЕЙНЕРА_ORDERS'
docker inspect "$PIZZA_ORDERS" --format '{{ index .Config.Labels "com.docker.compose.service" }}'
```

Результат должен быть `orders`. Иначе остановитесь: выбран не тот контейнер.

2. Введите реальные данные администратора, пароль уникальный 16+ символов:

```bash
read -r -p 'Email администратора пиццерии: ' BOOTSTRAP_ADMIN_EMAIL
read -r -s -p 'Пароль администратора (16+ символов): ' BOOTSTRAP_ADMIN_PASSWORD
printf '\n'
export BOOTSTRAP_ADMIN_EMAIL BOOTSTRAP_ADMIN_PASSWORD
docker exec -e BOOTSTRAP_ADMIN_EMAIL -e BOOTSTRAP_ADMIN_PASSWORD -e SEED_DEMO_ACCOUNTS=false "$PIZZA_ORDERS" node libs/prisma/dist/seed.js
unset BOOTSTRAP_ADMIN_EMAIL BOOTSTRAP_ADMIN_PASSWORD
```

Ключи не печатаются в командной строке: `docker exec -e ИМЯ` берёт экспортированное значение. Это явная передача bootstrap-полей, которых нет в обычном terminal orders.

3. Дождитесь `Seed complete`. Войдите на `/login`, откройте `/admin`.
4. Проверьте товары, цены, фото/вкусы Kinza, ингредиенты, филиалы, часы, зону доставки и контакты. Примерные адреса/телефоны не считаются подтверждёнными данными пиццерии.
5. Проверьте начальный `WELCOME10`: выключите, если бизнес его не утверждал. Тестовый `E2EALWAYS10` production seed больше не создаёт.
6. `Admin123!`/`Customer123!` — только локальные demo-пароли. Они не создаются в этом запуске. Если переносили старую локальную БД, отдельно устраните demo-пользователей/тестовые заказы/промокоды.
7. Если нужен перенос локальной БД, **не выполняйте этот seed**: перенос дампа и очистка тестовых данных — отдельная процедура.

## 15. Проверить реального покупателя

1. Откройте приватное окно браузера, чтобы не смешать покупателя с администратором.
2. Зарегистрируйте новый email, подтвердите согласие, дождитесь настоящего письма, проверьте spam. Введите код и войдите.
3. Добавьте пиццу с размером/добавками и Kinza с вкусом; проверьте сумму и фото. Создайте адрес, удалите и добавьте снова.
4. Выберите доставку либо самовывоз. Для доставки нужен адрес, для самовывоза — филиал. Вне часов работы используйте допустимый слот «Ко времени».
5. Предупредите сотрудников и оформите согласованный тестовый заказ с комментарием **`ТЕСТ ЗАПУСКА — НЕ ГОТОВИТЬ`**, оплатой при получении.
6. В админском окне проверьте заказ/кухню, вкус, размер, время, адрес, цену. У покупателя статус должен обновляться.
7. Отмените тест до приготовления, проверьте статус/возврат баллов и промокода, если применялись.
8. Проверьте обращение поддержки с кириллицей и ответ оператора без дублей. Проверьте сброс пароля тестового аккаунта и настоящее письмо.
9. Проверьте с телефона через мобильный интернет: HTTPS, меню, корзина, регистрация, checkout. Зелёный Deploy не заменяет эти проверки.

## 16. Подключить ЮKassa после первого запуска

1. Создайте кабинет и **тестовый магазин**, получите Shop ID/секретный ключ. Тестовый режим не переводит реальные деньги.
2. В Environment укажите оба реквизита одного магазина, сохраните, Deploy. Клиент для серверных ключей пересобирать не нужно.
3. В ЮKassa настройте HTTP-уведомления на `https://ВАШ_ДОМЕН/api/payments/webhook`, события `payment.succeeded`, `payment.canceled`.
4. Оформите тестовый онлайн-заказ. Оплата идёт на странице ЮKassa. Используйте тестовую карту из её документации.
5. Проверьте успех, отказ банка, повтор оплаты, отмену/возврат и точное совпадение сумм. Не отмечайте платёж успешным только по возврату браузера на сайт.
6. До боевых ключей согласуйте договор и кассу. Фискальные переменные задаются по вашему бизнесу, не по случайному НДС из примера.
7. Код передаёт чек **предоплаты** и полного возврата. Чек зачёта предоплаты при выдаче и маркировка напитков требуют кассы/учётной системы. Один флаг `true` этого не настраивает.
8. После договора/кассы замените оба ключа боевыми, Deploy, проведите согласованный проверочный платёж и возврат с владельцем. Затем разрешайте онлайн-оплату покупателям.

Полные параметры — [PAYMENTS_YOOKASSA.md](PAYMENTS_YOOKASSA.md). Терминал/наличные при получении обслуживает касса пиццерии.

## 17. Сделать резервную копию вне VPS

Volumes переживают обычный Deploy, но не потерю VPS. Нужен логический dump PostgreSQL и проверка восстановления.

1. Найдите PostgreSQL этого проекта в `docker ps`. Проверьте имя:

```bash
PIZZA_POSTGRES='ИМЯ_КОНТЕЙНЕРА_POSTGRES'
docker inspect "$PIZZA_POSTGRES" --format '{{ index .Config.Labels "com.docker.compose.service" }}'
```

Должно быть `postgres`. На VPS:

```bash
install -d -m 700 /root/chicago-backups
umask 077
docker exec "$PIZZA_POSTGRES" sh -ec 'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > /root/chicago-backups/first-production.dump
ls -lh /root/chicago-backups/first-production.dump
```

2. В PowerShell компьютера скачайте:

```powershell
scp -i "$env:USERPROFILE\.ssh\chicago_aeza" root@IP_ВАШЕГО_VPS:/root/chicago-backups/first-production.dump "$env:USERPROFILE\Downloads\chicago-first-production.dump"
```

Дамп содержит личные данные — храните закрыто, не в Git. До каждого обновления делайте свежую копию, используя новое имя файла.

3. Проверьте восстановление в **новую тестовую БД**, не поверх production. Есть `scripts/restore-production-to-staging.sh`, требующий имя `restore_*` и отказ при существующей БД. Ниже настройки автоматизации дают окружение для этого скрипта.

### Ежедневные копии через restic

4. Выберите внешнее S3/SFTP-хранилище; оно должно находиться вне этого VPS. У поставщика получите endpoint, bucket/путь и учётные данные. Конкретный endpoint нельзя придумать: он зависит от услуги.
5. На VPS:

```bash
apt install -y restic
git clone https://github.com/IR-Full/chicago-pizza.git /opt/chicago-ops
umask 077
nano /opt/chicago-ops/.env
```

В этот закрытый `.env` скопируйте реальные Environment-значения вашего Compose из Dokploy, включая образы/DOMAIN/пароли. Это нужно для host-side Compose. Не коммитьте файл. `chmod 600 /opt/chicago-ops/.env`.

6. Узнайте фактическое имя проекта:

```bash
docker inspect "$PIZZA_POSTGRES" --format '{{ index .Config.Labels "com.docker.compose.project" }}'
```

Запишите результат — не используйте произвольное `chicago-pizza`. Создайте `nano /root/chicago-backup.env`:

```bash
COMPOSE_PROJECT_NAME=ИМЯ_ИЗ_ПРЕДЫДУЩЕЙ_КОМАНДЫ
RESTIC_REPOSITORY=s3:https://ВАШ_ENDPOINT/ВАШ_BUCKET
RESTIC_PASSWORD=ОТДЕЛЬНЫЙ_ДЛИННЫЙ_ПАРОЛЬ_ШИФРОВАНИЯ
AWS_ACCESS_KEY_ID=КЛЮЧ_ХРАНИЛИЩА
AWS_SECRET_ACCESS_KEY=СЕКРЕТ_ХРАНИЛИЩА
```

Это пример **S3**. Для SFTP вместо S3-адреса задают `sftp:ПОЛЬЗОВАТЕЛЬ@ХОСТ:/ПУТЬ` и заранее проверяют SSH-доступ с VPS к хранилищу. Не смешивайте реквизиты разных вариантов. Секреты без пробелов упрощают shell-файл; сложные значения заключайте в корректные кавычки.

7. `chmod 600 /root/chicago-backup.env`. Сохраните пароль restic отдельно от VPS: без него восстановление невозможно. Загрузите окружение и инициализируйте хранилище **один раз**:

```bash
set -a
source /root/chicago-backup.env
set +a
restic init
cd /opt/chicago-ops
bash scripts/backup-production.sh
restic snapshots
```

В snapshots должна появиться копия `chicago-pizza`. Скрипт хранит 7 дневных/4 недельных/6 месячных копий. При ошибке не переходите к cron, разберитесь с адресом/ключами/правами.

8. Создайте `nano /usr/local/sbin/chicago-backup`:

```bash
#!/usr/bin/env bash
set -euo pipefail
set -a
source /root/chicago-backup.env
set +a
cd /opt/chicago-ops
exec bash scripts/backup-production.sh
```

Затем:

```bash
chmod 700 /usr/local/sbin/chicago-backup
/usr/local/sbin/chicago-backup
crontab -e
```

Выберите nano, если предложено, и добавьте:

```cron
15 3 * * * /usr/local/sbin/chicago-backup >> /var/log/chicago-backup.log 2>&1
```

9. Это 03:15 по часовому поясу VPS. Сохраните и проверьте `crontab -l`. На следующий день проверьте новую snapshot и лог. Отдельно настройте уведомление о неуспешном запуске/отсутствии свежей копии: запись ошибки в файл сама вам не сообщает.
10. Для проверки restore, с загруженным окружением и из `/opt/chicago-ops`:

```bash
restic dump ID_НУЖНОЙ_SNAPSHOT database.dump > /root/chicago-backups/restore-check.dump
export RESTORE_DATABASE=restore_verification
bash scripts/restore-production-to-staging.sh /root/chicago-backups/restore-check.dump
```

Скрипт откажет, если `restore_verification` уже существует. Для новой проверки выберите новое `restore_*` имя. Проверьте чтение товаров/заказов в этой тестовой БД. Не подключайте покупателей к restore-базе. Более подробная операторская справка — [DEPLOY_DOKPLOY.md](DEPLOY_DOKPLOY.md).

## 18. Проверить ресурсы и мониторинг

На VPS:

```bash
docker stats --no-stream
free -h
df -h /
docker exec "$PIZZA_ORDERS" node ops/check-production.cjs
```

При обычной работе должен оставаться запас памяти и диска. OOM/restarts на 4 ГБ требуют увеличения тарифа; постоянный swap не является нормой. Ненулевой код monitor-скрипта требует расследования.

Настройте внешнюю проверку `https://ВАШ_ДОМЕН/health/ready`, уведомления о падении/неудачном Deploy, диск, рестарты и ошибки SMTP/возвратов. Раз в 1–5 минут запускайте monitor-скрипт планировщиком с оповещением владельца.

До открытия сайта сузьте `set_real_ip_from` в `infra/nginx/nginx.dokploy.conf` до фактической подсети, откуда Traefik подключается к Nginx. Узнать: `docker network inspect dokploy-network --format '{{json .IPAM.Config}}'`. Меняйте конфиг в Git, затем Deploy и проверка IP/лимитов; не включайте `forwardedHeaders.insecure`.

Проверьте `ss -lntp`: публичные сайт 80/443, ограниченный SSH; базы и management UI не публикуются. Назначьте сотрудникам нужные роли, не делайте каждого администратором. Проверьте реальные контакты, часы, адреса и документы магазина.

## 19. Обновления и откат

1. Свежий backup вне VPS и запись обоих текущих image-тегов.
2. Новые изменения в main → зелёный CI → Publish deployment images для того же домена.
3. В Dokploy замените **оба** image SHA, Save, Deploy. Миграции запустятся автоматически.
4. Seed при обновлении не запускается. Проверьте регистрацию/меню/checkout/поддержку после выпуска.
5. Откат кода — оба прежних image-тега, Deploy. БД от этого не откатывается; совместимость старого кода с новой схемой проверяют отдельно.
6. Не восстанавливайте вчерашнюю БД просто ради отката — потеряются новые заказы. Не используйте `down -v`, удаление volumes и переустановку VPS для обычного обновления.
7. Старые образы очищайте через Dokploy, сохраняя текущую и предыдущую рабочие версии. Следите за свободным диском.

## 20. Что делать при ошибке

| Симптом | Первая проверка |
| --- | --- |
| SSH timeout | VPS работает, IPv4/22 верны, правило вашего IP; консоль Aeza |
| Permission denied | Пользователь, ключ, authorized_keys, права 700/600 |
| Старый IP / domain not found | NS/A в Aeza, парковочные записи, время обновления |
| SSL не выдаётся | DNS A/AAAA, 80/443, домен и лог Traefik; не обходить предупреждение браузера |
| denied при скачивании | package visibility, registry login/срок токена, тег существует |
| no matching manifest | VPS x86_64, правильный образ и SHA |
| missing required variable | Environment сохранён, обязательные поля заполнены |
| Ошибка bind mount | Git-source всего репо, Compose path, наличие infra/nginx |
| migrate exited 0 | Нормальное успешное завершение |
| migrate exited не 0 | Лог migrate/БД; не удалять рабочую базу |
| 502 | Статусы client/gateway/nginx, сеть, домен nginx:80 |
| Пустое меню новой БД | Одноразовый seed ещё не выполнен |
| Нет писем | Host/порт/TLS/логин/From, SPF/DKIM/spam, logs notifications |
| Онлайн-карта недоступна | Оба ключа ЮKassa в orders и пересозданный контейнер |
| Старые URL / вход не работает | Правильный site_url сборки, DOMAIN/HTTPS, не перепутаны образы |
| OOM/restarts | RAM/лимиты/swap/диск, увеличение тарифа при подтверждённой нехватке |

Лог: `docker logs --tail 100 ИМЯ_КОНТЕЙНЕРА`. Не публикуйте секреты из логов. Ошибка конкретного шага полезнее повторной переустановки.

## 21. Условия открытия сайта покупателям

- DNS/HTTPS работают, панель защищена, прямой 3000 закрыт.
- Образы одного проверенного SHA, CI успешен, миграции применены.
- Ваш администратор создан, demo-аккаунтов нет, меню/контакты/часы утверждены.
- Настоящие письма доставляются; покупатель проходит регистрацию/сброс пароля.
- Проверены заказ, кухня, поддержка, отмена и отсутствие повторов.
- Есть внешние копии, проверка восстановления и оповещения о сбоях.
- Для онлайн-карты проверены платёж/возврат и фискализация; без этого действует оплата при получении.
- VPS выдерживает проверку без OOM и опасного заполнения диска.

После этого начинайте ограниченный запуск и наблюдайте за первыми реальными заказами.
