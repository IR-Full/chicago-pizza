# Chicago Pizza — сеть пиццерий (Махачкала)

Веб-приложение для заказа пиццы: каталог с конструктором пицц 50/50, корзина,
оформление заказа, отслеживание статуса в реальном времени, программа
лояльности, чат с поддержкой и панель управления для персонала.

**Стек:** NestJS-микросервисы + RabbitMQ + PostgreSQL + Redis · Next.js 14
(App Router, FSD) · Docker Compose + Nginx.

## Архитектура

```
                         ┌────────────────┐
   Браузер ──── HTTPS ───│     Nginx      │
        └──── WebSocket ─│ (reverse proxy)│
                         └───────┬────────┘
                    ┌────────────┴────────────┐
                    ▼                         ▼
          ┌──────────────────┐      ┌──────────────────┐
          │  Next.js client  │      │   API Gateway    │
          │  (SSR + RSC)     │      │ REST + Socket.IO │
          └──────────────────┘      └────────┬─────────┘
                                             │ RabbitMQ (request/response + events)
        ┌──────────┬───────────┬─────────────┼──────────────┐
        ▼          ▼           ▼             ▼              ▼
    ┌───────┐ ┌─────────┐ ┌────────┐ ┌──────────────┐ ┌─────────┐
    │ auth  │ │products │ │ orders │ │notifications │ │ support │
    └───┬───┘ └────┬────┘ └───┬────┘ └──────┬───────┘ └────┬────┘
        └──────────┴──────────┼─────────────┴──────────────┘
                     ┌────────┴─────────┐
                     ▼                  ▼
              ┌────────────┐     ┌────────────┐
              │ PostgreSQL │     │   Redis    │
              └────────────┘     └────────────┘
```

**Gateway — единственная публичная точка входа.** Микросервисы не слушают
HTTP вообще: они подключены только к RabbitMQ и недоступны снаружи. Gateway
проверяет аутентификацию и роли, валидирует входные данные, применяет
rate limiting и превращает HTTP-вызовы в RPC по очередям.

**Зоны ответственности сервисов:**

| Сервис | Отвечает за |
|---|---|
| `auth` | Регистрация, вход, JWT + ротация refresh-токенов, RBAC, адреса доставки |
| `products` | Каталог, ингредиенты, тесто, **расчёт цены**, избранное, рекомендации |
| `orders` | Корзина (Redis), оформление заказа, промокоды, статусы, лояльность, рефералы |
| `notifications` | Email через BullMQ + Nodemailer, лента уведомлений, Web Push-подписки |
| `support` | Тикеты и сообщения чата |
| `gateway` | REST API, Swagger, WebSocket-рассылка, безопасность |

**Redis** используется для трёх разных задач: кеш каталога (TTL 5 мин),
корзина (TTL 7 дней), счётчики брутфорса и rate limiting (TTL 1 мин), а также
как adapter для Socket.IO, чтобы рассылка работала при нескольких репликах
gateway.

### Real-time

Клиент держит одно Socket.IO-соединение. Аутентификация — та же httpOnly-кука
`access_token`, что и у REST, поэтому токен никогда не попадает в JavaScript.
При подключении сокет заходит в комнату `user:<id>`, персонал дополнительно в
`staff`. Комнаты `order:<id>` и `ticket:<id>` — для точечной подписки.

## Модель данных

Одна база PostgreSQL, разделённая по доменам. Каждый сервис работает только со
своими таблицами; межсервисные запросы идут через RabbitMQ, а не через JOIN
между доменами.

```
User ──< RefreshToken            User ──< Address ──< Order
     ──< EmailVerificationCode   User ──< Favorite >── Product
     ──< PasswordResetToken      User ──< LoyaltyTransaction
     ──< Referral                User ──< SupportTicket ──< TicketMessage
                                 User ──< Notification, PushSubscription

Category ──< Product ──< ProductSize
                     ──< ProductIngredient >── Ingredient

Order ──< OrderItem >── DoughType
      ──< OrderStatusHistory
      ──  Review (1:1)
      >── Promocode
```

Полная схема: [`server/libs/prisma/prisma/schema.prisma`](server/libs/prisma/prisma/schema.prisma).

> **Все денежные суммы хранятся в копейках** (`Int`), чтобы исключить ошибки
> округления с плавающей точкой. Форматирование в рубли — только на клиенте.

## Быстрый старт

**Требуется:** Docker + Docker Compose.

```bash
# 1. Настроить окружение
cp .env.example .env

# 2. Сгенерировать секрет (compose не стартует с плейсхолдером)
#    Linux/macOS:
sed -i "s|^JWT_ACCESS_SECRET=.*|JWT_ACCESS_SECRET=$(openssl rand -hex 32)|" .env

#    Windows (PowerShell) — впишите случайное значение вручную:
#    notepad .env

# 3. Поднять весь стек (первый запуск — с демо-каталогом)
SEED_ON_START=true docker compose up --build
```

Миграции выполняются автоматически контейнером `migrate` до запуска сервисов.
Сидирование — только при `SEED_ON_START=true`: сид работает на upsert'ах и при
каждом рестарте возвращал бы цены к заводским, затирая правки из админки.

Дальше:

| Что | Где |
|---|---|
| Сайт | http://localhost |
| Swagger UI | http://localhost/api/docs (в проде закрыт, см. `ENABLE_API_DOCS`) |
| Почта (MailHog) | http://localhost:8025 — профиль `dev` |
| RabbitMQ UI | http://127.0.0.1:15672 (`pizza` / `pizza`) |

**Тестовый администратор:** `admin@chicago-pizza.ru` / `Admin123!`

**Промокод для проверки:** `WELCOME10` — 10% при заказе от 500 ₽.

> Коды подтверждения email и ссылки восстановления пароля приходят в MailHog,
> реальная почта не отправляется.

### Полезные команды

```bash
docker compose logs -f gateway      # логи одного сервиса
docker compose restart orders       # перезапустить сервис
docker compose down -v              # остановить и стереть данные
docker compose up -d --build client # пересобрать только фронтенд
```

Первый запуск на пустой базе: наполнить каталог демо-данными можно один раз,
явным флагом — сид работает на upsert'ах и иначе перезатрёт цены, изменённые
через админку:

```bash
SEED_ON_START=true docker compose up -d migrate
```

## Локальная разработка без Docker

Инфраструктуру всё равно удобнее держать в контейнерах:

```bash
docker compose --profile dev up -d postgres redis rabbitmq mailhog
```

> MailHog живёт в профиле `dev` — в продовом стеке он не поднимается вовсе.
> Порты Postgres и RabbitMQ-UI публикуются только на `127.0.0.1`.

**Backend:**

```bash
cd server
npm install
npm run build:libs        # prisma generate + сборка общих библиотек

# .env в папке server/ (для локального запуска)
# DATABASE_URL=postgresql://pizza:pizza@localhost:5432/chicago_pizza?schema=public
# REDIS_URL=redis://localhost:6379
# RABBITMQ_URL=amqp://pizza:pizza@localhost:5672
# CLIENT_URL=http://localhost:3000
# JWT_ACCESS_SECRET=<32+ символа>
# SMTP_HOST=localhost
# SMTP_PORT=1025
# PORT=4000

npm run prisma:migrate
npm run prisma:seed

# каждый сервис в своём терминале
npm run dev:gateway
npm run dev:auth
npm run dev:products
npm run dev:orders
npm run dev:notifications
npm run dev:support
```

**Frontend:**

```bash
cd client
npm install

# client/.env.local
# NEXT_PUBLIC_API_URL=http://localhost:4000/api
# NEXT_PUBLIC_WS_URL=http://localhost:4000
# INTERNAL_API_URL=http://localhost:4000/api
```

> Библиотеки в `server/libs/*` собираются через TypeScript project references.
> После правок в них выполните `npm run build:libs`, иначе сервисы увидят

## Ключевые доменные решения

**Цену всегда считает сервер.** Конструктор пиццы запрашивает цену у
`products` при каждом изменении, а при оформлении заказа корзина
пересчитывается заново. Клиент никогда не присылает сумму — подделать её
невозможно.

**Правила расчёта:**
- База — цена выбранного размера (30 / 45 / 60 см).
- Пицца 50/50 стоит как **более дорогая** половинка.
- Тесто добавляет фиксированную надбавку.
- Каждый добавленный ингредиент платный, удаление ингредиентов бесплатно и
  скидки не даёт.
- Доставка 150 ₽, бесплатно от 1000 ₽.

**Корзина живёт в Redis**, а не в PostgreSQL: это высокочастотное временное
состояние. Хранится только *конфигурация* позиций, цены подставляются при
каждом чтении.

**Статусы заказа — конечный автомат.** Разрешены только переходы
`CREATED → ACCEPTED → PREPARING → ON_DELIVERY → DELIVERED` (и отмена на любом
шаге до доставки). Попытка «отмотать» доставленный заказ отклоняется.

**Лояльность:** кэшбэк 5 / 7 / 10 % для уровней BRONZE / SILVER / GOLD, уровень
пересчитывается по сумме доставленных заказов. 1 балл = 1 ₽. Баллы и
реферальный бонус (300 баллов) начисляются **только после статуса
DELIVERED** — в одной транзакции с обновлением заказа.

## Безопасность

| Мера | Реализация |
|---|---|
| Хранение паролей | bcrypt, 12 раундов |
| Токены | JWT access (15 мин) + opaque refresh (30 дней) |
| Ротация refresh | Каждое обновление отзывает старый токен |
| Защита от кражи токена | Повторное использование отозванного токена ⇒ отзыв **всех** сессий пользователя |
| Хранение refresh-токенов | Только SHA-256 хеш — утечка БД не даёт рабочих токенов |
| Куки | `httpOnly`, `SameSite=Lax`, `Secure` в проде; refresh-кука ограничена путём `/api/auth` |
| XSS | Токены недоступны из JS; React экранирует вывод; CSP объявляется в `next.config.mjs` (HTML отдаёт Next, а не gateway) |
| HTML-инъекция в письмах | Имя и тема обращения экранируются в шаблонах |
| Брутфорс | Счётчик по паре «аккаунт + источник» (5 попыток) и по аккаунту целиком (50); для несуществующего email выполняется холостой `bcrypt.compare`, чтобы время ответа не выдавало наличие аккаунта |
| Перебор кода подтверждения | 5 попыток на аккаунт, после чего выданные коды сжигаются |
| Rate limiting | 100 запросов/мин на IP в Redis (общий счётчик для всех реплик) + отдельные лимиты на auth-эндпоинты + `limit_req`/`limit_conn` в Nginx |
| TLS | `nginx.tls.conf`: TLS 1.2/1.3, редирект с :80, HSTS на 2 года, OCSP stapling; сертификат обновляет certbot |
| SQL-инъекции | Только параметризованные запросы Prisma |
| Валидация | `class-validator` на каждом DTO; `whitelist: true` (неизвестные поля отбрасываются, а не отклоняются — маркетинговая ссылка с `utm_source` не должна падать с 400) |
| Конфигурация | Проверка env через Zod при старте — сервис не поднимется с неверными настройками |
| Авторизация | RBAC-гварды на gateway + повторная проверка владельца ресурса в сервисах; курьер видит только свои и ещё не разобранные заказы |
| WebSocket | Подписка на заказ или тикет проверяет владение через тот же RPC, что и REST; сокет закрывается при истечении токена и при отзыве сессии (Redis pub/sub) |
| Смена роли / блокировка | Немедленный отзыв всех сессий пользователя, включая открытые сокеты |
| Утечка данных | Ответы на регистрацию, «забыл пароль» и повторную отправку кода одинаковы для существующих и несуществующих email; владельцу занятого адреса уходит письмо |
| Журнал действий | `AdminAuditLog`: смена роли, блокировка, статус заказа, правки каталога и промокодов, удаление аккаунта |
| Персональные данные | Согласие с версией документа при регистрации, выгрузка данных, удаление аккаунта с обезличиванием, список активных сессий; email и токены не попадают в логи |
| Зависимости | `scripts/audit-gate.mjs` валит сборку на любой непроверенный advisory уровня high+; Dependabot, CodeQL, gitleaks и Trivy в CI |

## HTTPS

По умолчанию стек слушает только `:80` — так удобно для локального запуска и
CI. Прод терминирует TLS в nginx; переключение — через `.env`:

```bash
NGINX_CONF=nginx.tls.conf
DOMAIN=chicago-pizza.ru
CLIENT_URL=https://chicago-pizza.ru
NEXT_PUBLIC_API_URL=https://chicago-pizza.ru/api
NEXT_PUBLIC_WS_URL=https://chicago-pizza.ru
```

Первый сертификат выпускается один раз, до переключения конфига — пока стек
ещё на `:80`, чтобы ACME-проверка прошла:

```bash
docker compose up -d nginx
docker compose run --rm --entrypoint certbot certbot certonly   --webroot -w /var/www/certbot   -d "$DOMAIN" --email admin@"$DOMAIN" --agree-tos --no-eff-email
```

После этого меняем `NGINX_CONF` и пересоздаём прокси:

```bash
docker compose up -d --force-recreate nginx client
```

Продление берёт на себя контейнер `certbot` из профиля `tls`
(`docker compose --profile tls up -d`): он просыпается каждые 12 часов и
молча выходит, если продлевать нечего.

Куки помечаются `Secure` автоматически — признак выводится из схемы
`CLIENT_URL`, а не из `NODE_ENV`: compose-стек работает с `NODE_ENV=production`
и на голом HTTP, и привязка к `NODE_ENV` тихо ломала бы вход на localhost.
Если TLS терминируется выше по стеку (балансировщик, Cloudflare), поставьте
`COOKIE_SECURE=true` явно.

## Персональные данные

Сервис хранит имя, email, телефон и адрес доставки — это обработка
персональных данных по 152-ФЗ, поэтому она устроена так:

| Право | Где |
|---|---|
| Согласие | Чекбокс при регистрации; в БД пишется **версия** документа (`consentVersion`), а не флаг — при изменении политики согласие нужно взять заново |
| Политика | `/privacy`, версия проставляется из `shared/config/legal.ts` |
| Копия данных | Профиль → «Скачать мои данные»: профиль, адреса, заказы, баллы и переписка с поддержкой одним JSON |
| Удаление | Профиль → «Удалить аккаунт»: имя, email, телефон, адреса, пароль и сообщения стираются; заказы остаются обезличенными, как того требует бухгалтерский учёт |
| Активные сессии | Профиль → список входов с IP и устройством, чужую сессию можно завершить |
| Журнал действий | Таблица `admin_audit_logs` — кто, что и над кем сделал |

В логах персональных данных нет: адреса маскируются (`g***t@chicago.ru`),
из URL вырезаются `token`, `code`, `email`, `phone` и `search`, идентификаторы
пользователей сокращаются до восьми символов.

Каждый HTTP-запрос получает `X-Request-Id`; тот же идентификатор уходит в
RabbitMQ и попадает в логи всех шести сервисов, так что «упало в 14:32»
превращается в один `grep` вместо шести.

Тестами покрыта бизнес-логика, где ошибка стоит дороже всего: расчёт цены,
валидация промокодов, автомат статусов заказа, контроль доступа к заказам и
ротация refresh-токенов. Часть тестов — регрессионные: они закрывают баги,
найденные при живом прогоне стека (проброс HTTP-статуса через RabbitMQ,
флаг `Secure` у кук на HTTP, `@ValidateNested` у вложенных DTO).

### Что проверено на живом стеке

Сборка поднималась через `docker compose up` и проверялась вручную end-to-end:

- каталог, фильтры и поиск по ингредиентам («шампиньоны» → Ассорти, Грибная,
  Жюльен);
- расчёт цены: 45 см = 63000, сырное тесто +15000, бекон +11000,
  50/50 с Мясной = 71000 (цена дорогой половинки);
- регистрация → письмо с кодом в MailHog → подтверждение → вход по куке;
- корзина (199000 коп.), промокод WELCOME10 (−19900), заказ на 179100 коп.
  с бесплатной доставкой;
- полный цикл статусов CREATED → … → DELIVERED, запрет недопустимых переходов
  (400, а не 500);
- начисление 89 баллов кэшбэка и автоматический переход BRONZE → SILVER;
- контроль доступа: владелец 200, другой клиент 403, аноним 401,
  админ-API для обычного пользователя 403;
- чат поддержки: тикет, ответ админа, автоперевод OPEN → IN_PROGRESS;
- WebSocket: обновление статуса заказа доходит до клиента ровно один раз;
- SSR главной страницы с реальными данными из БД, Swagger UI, PWA-манифест,
  service worker и офлайн-страница.

## Что реализовано и что нет

### Реализовано

- Регистрация и вход по email, подтверждение кодом, восстановление пароля
- JWT + ротация refresh-токенов с детектом повторного использования
- RBAC: `USER`, `ADMIN`, `COURIER`, `SUPPORT`
- Каталог: 9 пицц, закуски, напитки, десерты, комбо; фильтры и поиск по
  ингредиентам
- Конструктор пиццы: размеры, три вида теста, половинки 50/50,
  добавление и удаление ингредиентов, live-цена
- Корзина в Redis, промокоды, списание баллов лояльности
- Оформление заказа: адреса, доставка «сейчас» или ко времени, комментарий
- Статусы заказа в реальном времени через WebSocket
- История заказов и повтор заказа, оценка 1–5 звёзд
- Программа лояльности (уровни и кэшбэк) и реферальная система
- Чат с поддержкой и тикет-система
- Email-уведомления через очередь BullMQ с ретраями
- Избранное, персональные рекомендации
- Админ-панель: заказы, промокоды, пользователи, обращения
- i18n (RU/EN), тёмная тема, PWA с офлайн-страницей
- Docker Compose, Nginx, CI (сборка, тесты, аудит, E2E)

### Осознанно не реализовано

| Из ТЗ | Почему и что вместо этого |
|---|---|
| **Онлайн-оплата** (ЮKassa / CloudPayments) | Требует реальных ключей и юрлица. Сейчас — оплата картой или наличными курьеру; `PaymentMethod` в схеме готов к расширению |
| **SMS-подтверждение** (Twilio / SMS.ru) | Требует платного аккаунта. Вместо этого — подтверждение по email, поток кода идентичен |
| **Web Push (FCM)** | Подписки сохраняются, обработчик `push` в service worker готов; не хватает только VAPID-ключей и отправителя |
| **Карта 2GIS в чекауте** | Адрес вводится текстом; поля `lat`/`lng` есть в схеме и API — интеграция сводится к подключению виджета карты |
| **ML-рекомендации** | Нужен объём заказов, которого у нового проекта нет. Реализована эвристика: популярное минус уже заказанное |
| **Prometheus / Grafana / ELK / Jaeger** | Не поднимаются в compose. Логи идут в stdout с ограничением размера, health-чеки (`/health/live`, `/health/ready`) есть, сквозной `X-Request-Id` связывает запись во всех шести сервисах — подключение коллектора не требует правок кода |
| **Kubernetes, репликация PostgreSQL, Redis Cluster** | Избыточно для одной пиццерии. Сервисы stateless и масштабируются горизонтально: состояние сессий и корзины в Redis, WebSocket через Redis-adapter |
| **2FA, GeoIP-блокировка** | Не входит в MVP; базовая защита от брутфорса и блокировка аккаунтов есть |
| **A/B-тестирование, GA4 / Яндекс.Метрика** | Не подключены — требуют реальных идентификаторов счётчиков |
| **Отдельная БД на сервис** | Одна PostgreSQL с разделением по доменам. Схема-на-сервис потребовала бы saga/outbox для распределённых транзакций — неоправданная сложность на этом масштабе |

### Известные ограничения

- Корзина доступна только авторизованным пользователям (хранится в Redis по
  `userId`). Гостевая корзина в localStorage не реализована.
- Изображения товаров не загружены — карточки показывают эмодзи-плейсхолдер.
  Поле `imageUrl` в схеме есть, нужен только файловый storage или CDN.
- Иконки PWA — однотонные плейсхолдеры фирменного цвета; замените на
  настоящий логотип перед публикацией в сторах.
- Lighthouse-аудит не прогонялся: нужен реальный деплой с изображениями и HTTPS.
- `next/image` отключён (`unoptimized: true`): изображений в проекте пока нет,
  а открытый `/_next/image` работал как прокси для любого https-адреса.
  Включается обратно вместе с картинками — с перечислением реального хоста
  в `remotePatterns`.
- В дереве зависимостей остаётся `multer@2.2.0`: `@nestjs/platform-express`
  пинит его точной версией, и override до неё не достаёт. Эндпоинтов,
  принимающих `multipart/form-data`, в проекте нет, поэтому advisory
  недостижим — исключение задокументировано в `scripts/audit-waivers.json`
  со сроком, после которого сборка снова начнёт падать.
