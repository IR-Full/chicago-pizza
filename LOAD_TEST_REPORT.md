## Контроль непрерывности и результата

обёртки. Ноутбук должен оставаться на зарядке с открытой крышкой и работающим Docker.
Ручной сон, закрытие крышки и выключение могут прервать измерение.
При выявленной приостановке Windows более 5 секунд или интервале между наблюдениями
более 90 секунд обёртка остановит генератор и сохранит причину прерывания.

Раз в минуту собираются CPU/RAM, состояние контейнеров, перезапуски/OOM и время
бодрствования Windows. HTTP-ошибки и тайм-ауты сохраняются. Для успешного вывода нужны
полные восемь часов, отсутствие ошибок и разрывов мониторинга, проверенный итоговый JSON.
p95 и максимум относятся к последним 20 000 запросов; счётчики статусов охватывают весь прогон.
Это проверка устойчивости под указанной нагрузкой на локальном компьютере;

## Дополнительная диагностика тайм-аутов 17 октября

Механизм ошибок установлен, первопричина задержки — **нет**. Генератор прекратил
ожидание девяти запросов по лимиту 15 секунд. Восемь записей Nginx HTTP 499
согласуются с закрытием соединений клиентом до получения ответа; этот код описывает
последствие, а не источник задержки ([исходник Nginx](https://raw.githubusercontent.com/nginx/nginx/release-1.27.5/src/http/ngx_http_request.h)).
Девятый тайм-аут был на `/health/ready`: для `/health/` в конфигурации установлен
`access_log off`, поэтому отдельной строки access-журнала для него нет.

Во время эпизода внутренние `/health/live` завершались в **17:28:33 и 17:28:44 МСК**,
время в interceptor — 0 и 1 мс. Это свидетельство работы приложения в эти моменты,
но не исключение задержки остальных запросов: interceptor фиксирует завершение
обработки и начинает измерение после guards, а время поступления не пишет.
Отсутствие строки о неуспешном API-запросе не доказывает, что он не поступил в API.
Стандартный access-журнал Nginx также не содержит `$request_time`, времени upstream
и общего идентификатора запроса ([описание формата и переменных](https://nginx.org/en/docs/http/ngx_http_log_module.html)).
Поэтому отличить задержку на пути Windows → порт Docker → Nginx от задержки
между Nginx, guards и зависимостями приложения по этим данным нельзя.

Дополнительно проверены Redis и Redis Cache: сохранённые журналы не показывают
ошибок в эпизоде. В Windows около 17:28 нет событий Kernel-Power; снимки теста
также не выявили сон или перезапуск. Два события Huawei PC Manager о повторной
установке той же схемы питания не устанавливают причину: таких событий за время
прогона 1 433, в том числе вне эпизода ошибок. Системные журналы Docker/VM за
нужную минуту уже вытеснены ротацией; журналы контейнеров сохранены.

Короткая диагностическая проверка после завершения теста: **90 секунд**, только
`/health/ready`, три пути параллельно, примерно один запрос/с на каждый путь.

| Путь | HTTP 200 / запросы | p95 | Максимум |
| --- | --- | --- | --- |
| Windows → опубликованный порт → Nginx → API | 89 / 89 | 32 мс | 63 мс |
| Внутри Docker → Nginx → API | 90 / 90 | 13,431 мс | 50,6 мс |
| Внутри контейнера gateway → API напрямую | 90 / 90 | 9,769 мс | 19,995 мс |

Все **269 запросов успешны**, задержка не воспроизвелась. Это короткая проверка

Исходные девять ошибок сохраняются. Aeza и production не участвовали в маршруте
локального теста, поэтому относить этот эпизод к сбою хостинга оснований нет.

ожидания ответа у клиента, времени запроса и upstream в Nginx, отметка поступления
до guards с тем же идентификатором и своевременно сохранённые системные журналы
Docker. В ходе этой диагностики конфигурация, приложение и production не менялись.
