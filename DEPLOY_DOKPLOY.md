# Chicago Pizza: запуск на Aeza через Dokploy

Если запускаете VPS впервые, начните с [подробной инструкции для новичка](DEPLOY_AEZA_BEGINNER.md): покупка VPS/домена, PowerShell/SSH, DNS, Dokploy, заполнение Environment, запуск, почта, оплата и резервные копии. Этот файл — более короткая операторская справка.

Эта инструкция рассчитана на **первый запуск**, один VPS и сборку образов в GitHub Actions. Не включайте реальную онлайн-оплату до проверки платежей и возвратов в тестовом магазине ЮKassa.

## 1. Сервер и домен

Для экономного старта выбирайте самый дешёвый тариф Aeza с **2 vCPU, 4 ГБ RAM, 40+ ГБ SSD/NVMe и публичным IPv4**, архитектура x86_64. Это предварительная инженерная оценка, а не подтверждённый нагрузочным тестом минимум: перед открытием сайта измерьте память и проверьте оформление заказов при одновременном использовании админки. При нехватке памяти потребуется увеличить тариф. Здесь одновременно работают PostgreSQL, RabbitMQ, два Redis, шесть серверных процессов, Next.js и Dokploy. Сам Dokploy требует минимум 2 ГБ RAM и 30 ГБ диска; тарифы с 1–2 ГБ не выбираем для всего приложения. Сборку выполняем в GitHub Actions, не на VPS. 8 ГБ дают запас, но не являются обязательным условием для пробного запуска.

ОС по вашему пожеланию — **Ubuntu Server 26.04 LTS** (последняя LTS на дату подготовки). Docker официально поддерживает её, однако список проверенных ОС Dokploy пока включает 24.04 LTS, а 26.04 не перечисляет. Поэтому установку Dokploy на 26.04 необходимо проверить на новом сервере до загрузки данных; запасной проверенный вариант — 24.04 LTS. См. [Ubuntu 26.04](https://documentation.ubuntu.com/release-notes/26.04/) и [поддерживаемые ОС Docker](https://docs.docker.com/engine/install/ubuntu/).

Для пробного запуска на 4 ГБ добавьте в Environment параметры ниже. Они уменьшают резерв PostgreSQL и объём Redis; лимиты Node оставлены штатными, чтобы не вызвать принудительное завершение процессов слишком низким потолком. Это не гарантирует, что суммарное потребление уложится в 4 ГБ. Проверяйте `docker stats`, отсутствие OOM/restarts и свободный диск; удаляйте старые образы средствами Dokploy. Swap 2 ГБ может помочь пережить кратковременный пик, но не заменяет RAM.

```dotenv
POSTGRES_MAX_CONNECTIONS=100
POSTGRES_SHARED_BUFFERS=128MB
POSTGRES_EFFECTIVE_CACHE_SIZE=512MB
POSTGRES_WORK_MEM=4MB
POSTGRES_MAINTENANCE_WORK_MEM=32MB
STATE_REDIS_MAXMEMORY=192mb
CACHE_REDIS_MAXMEMORY=64mb
```

Выберите доступную у Aeza локацию с хорошей задержкой до Махачкалы. Проверьте IPv4, возможность установки Ubuntu, условия резервных копий, доступность исходящего SMTP и доступ к GitHub Container Registry. Актуальную цену смотрите в кабинете: фиксированный тариф здесь не обещается.

Если доступен `chicago-pizza.ru`, можно использовать его для сайта, а `panel.chicago-pizza.ru` для панели. Доступность домена не проверена. Создайте DNS A-записи обоих имён на IPv4 сервера. В примерах ниже `pizza.ВАШ_ДОМЕН` означает выбранное имя сайта, в том числе корневой `chicago-pizza.ru`. AAAA добавляйте только если IPv6 действительно настроен. Домен сайта должен совпадать с URL, с которым собирается клиент.

Официальные источники:

- [Aeza VPS/VDS](https://aeza.ru/virtual-servers)
- [Установка Dokploy](https://docs.dokploy.com/docs/core/installation)
- [Домены Docker Compose](https://docs.dokploy.com/docs/core/docker-compose/domains)

## 2. Установка Dokploy

Подключитесь по SSH ключом. На новом сервере проверьте, что порты 80, 443 и 3000 свободны. Скачайте официальный установщик, просмотрите его и запустите от root:

```bash
curl -fsSL https://dokploy.com/install.sh -o /tmp/dokploy-install.sh
less /tmp/dokploy-install.sh
sudo sh /tmp/dokploy-install.sh
```

Сразу создайте владельца панели по `http://IP:3000`, настройте HTTPS для `panel.ВАШ_ДОМЕН`, включите 2FA. До регистрации ограничьте 3000 своим IP. После проверки HTTPS уберите публикацию порта панели по инструкции Dokploy. SSH ограничьте своим IP/VPN; публичными остаются 80/443. Не открывайте PostgreSQL, Redis, RabbitMQ и Swarm management в интернет. Учитывайте правила Docker при настройке firewall: одного UFW недостаточно для опубликованных Docker-портов.

## 3. Сборка образов

Перед публикацией проверьте CI текущего коммита. В GitHub Actions запустите **Publish deployment images**, указав `https://pizza.ВАШ_ДОМЕН` без завершающего слеша. Workflow создаёт два образа с неизменяемым тегом commit SHA:

```text
ghcr.io/OWNER/REPOSITORY-server:SHA
ghcr.io/OWNER/REPOSITORY-client:SHA
```

Production Compose использует актуальные на дату подготовки RabbitMQ 4.3.6 и Nginx 1.30.5. Он предназначен для новых volumes: существующую RabbitMQ 3.13 нельзя напрямую обновлять до 4.3; нужен поддерживаемый путь через 4.2 и отдельная проверка миграции ([инструкция RabbitMQ](https://www.rabbitmq.com/docs/upgrade)).

Не используйте `latest` для рабочих деплоев. В Dokploy добавьте доступ к GHCR (read-only токен с `read:packages`, если пакеты приватные). Проверьте права на приватные пакеты. Публичные переменные Next.js встраиваются при сборке: изменение домена или ключа карты требует нового клиентского образа.

## 4. Создание проекта в Dokploy

1. Создайте Project → Docker Compose, источник — Git-репозиторий.
2. Выберите **Compose**, не Docker Stack. Compose path: `docker-compose.dokploy.yml`.
3. В Environment перенесите шаблон `.env.dokploy.example` и заполните все обязательные поля. Каждому паролю — отдельный `openssl rand -hex 32`. Пароли в URL должны быть URL-safe.
4. `SERVER_IMAGE` и `CLIENT_IMAGE` — образы одного проверенного SHA. `DOMAIN` — только имя хоста, без `https://`.
5. В Domains добавьте домен **к сервису `nginx`, порту 80**, включите HTTPS/Let's Encrypt. Не добавляйте домены к gateway, client, БД и брокеру. Сеть `dokploy-network` должна существовать.
6. Deploy. Сервис `migrate` применяет миграции и завершается; серверные процессы стартуют только после его успеха.

Nginx не занимает 80/443 хоста — их обслуживает Traefik Dokploy. Репозиторий должен быть доступен целиком: Compose монтирует конфиги из `infra/nginx`. Не заменяйте Git-source вставкой одного YAML без файлов.

После установки проверьте подсеть `docker network inspect dokploy-network` и сузьте доверенные диапазоны `set_real_ip_from` в `infra/nginx/nginx.dokploy.conf` до её фактической подсети. Не включайте `forwardedHeaders.insecure` у Traefik. Иначе можно подменить IP для лимитов.

## 5. Меню и первый администратор

Автоматического seed на каждом деплое **нет**: он перезаписывает меню. Укажите `BOOTSTRAP_ADMIN_EMAIL` и уникальный `BOOTSTRAP_ADMIN_PASSWORD` (минимум 16 символов), затем один раз из Git-checkout на сервере выполните команду ниже. Для неё загрузите защищённый env-файл с параметрами Compose и задайте фактический `COMPOSE_PROJECT_NAME` из `docker compose ls` (как для backup в разделе 7). Bootstrap-переменные передаются только сервису `migrate`, поэтому терминал `orders` для этого не подходит.

```bash
docker compose -f docker-compose.dokploy.yml run --rm --no-deps migrate node libs/prisma/dist/seed.js
```

В production запрещены демонстрационные аккаунты. `SEED_DEMO_ACCOUNTS=false`; известные `Admin123!` и `Customer123!` создаются только при явном demo-режиме локального стенда. После первого входа уберите bootstrap-пароль из Environment. При переносе уже засидированной базы смените известные пароли или удалите demo-пользователей до открытия сайта.

Проверьте филиалы, часы, адреса, цены, зоны доставки и реальные контакты. При первом запуске seed содержит примерный промокод: проверьте, нужен ли он бизнесу. Повторный seed после редактирования меню не является процедурой деплоя.

## 6. Почта и платежи

Укажите реальные `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`, порт и TLS-настройку своего почтового сервиса. Проверьте SPF/DKIM и доставку писем регистрации/сброса пароля. MailHog в production отсутствует.

Без `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` онлайн-оплата выключена. Сначала используйте тестовые реквизиты. В ЮKassa настройте webhook на:

```text
https://pizza.ВАШ_ДОМЕН/api/payments/webhook
```

Проверьте точный маршрут в `server/apps/gateway/src/controllers/orders.controller.ts`: при изменении кода он является источником истины. Проверьте успешную оплату, отказ банка, потерянный webhook, оплату после отмены, pending/canceled возврат и повтор запроса. Состояние провайдера дополнительно сверяется фоновым процессом раз в минуту. Отменённый провайдером возврат требует действий оператора — деньги нельзя считать возвращёнными.

Настройте чеки по [PAYMENTS_YOOKASSA.md](PAYMENTS_YOOKASSA.md). При `YOOKASSA_RECEIPT_ENABLED=true` сервер передаёт чек предоплаты в платёж и сохраняет его для полного возврата. Ставку НДС и систему налогообложения укажите явно по настройкам бизнеса; не выбирайте их наугад. При выдаче заказа касса должна сформировать чек зачёта предоплаты. Реальную фискализацию нужно проверить в кабинете кассы и ЮKassa.

## 7. Резервные копии и восстановление

Постоянные volumes сохраняют данные между деплоями; это **не резервная копия**.
На опубликованном стенде используется отдельный `docker-compose.backups.yml`:
каждый час в :15 МСК сохраняются обе БД, Redis состояния и настройки Dokploy
в зашифрованное внешнее хранилище. Полная настройка, хранение и восстановление —
в [BACKUP_OPERATIONS.md](BACKUP_OPERATIONS.md).

Пароль restic и S3-ключи держите отдельно от VPS. Проверяйте свежесть копий и письма
об ошибках, ежемесячно повторяйте восстановление в изолированные контейнеры.
Перед миграциями нужна свежая копия. Не запускайте одновременно отдельный ночной
host-side скрипт или установленное ранее systemd-задание вместе с действующим
backup-worker без согласованной схемы хранения. Поддерживаемые файлы проекта описывают Compose-worker.

## 8. Мониторинг и выпуск

В терминале `orders` или через Compose запускайте каждые 1–5 минут:

```bash
node ops/check-production.cjs
```

Ненулевой код требует оповещения владельца. Проверяются застрявшие outbox-события, невозвращённые платежи, canceled возвраты, readiness gateway и отсутствие eviction у state Redis. Дополнительно настройте внешний HTTPS uptime-monitor, диск (предупреждение от 80%), RAM, рестарты контейнеров и неуспешные BullMQ email jobs.

В контейнере RabbitMQ проверяйте:

```bash
rabbitmqctl list_queues name messages_ready messages_unacknowledged
```

Непустые `*.dead`, рост очередей и неподтверждённых сообщений требуют расследования. Не публикуйте management UI; используйте Dokploy terminal/SSH. Не очищайте очереди как способ исправления ошибки.

Release gate: CI + production build → staging с HTTPS → регистрация/почта → checkout/двойной submit → кухня → оплата/возврат → backup/restore → ограниченный запуск с наблюдением. При обновлении изменяйте оба SHA вместе, сохраняйте предыдущие теги. Откат кода не откатывает миграции; данная миграция добавляет поля и совместима со старым чтением, но при откате старый код снова содержит исправленные ошибки. Не запускайте `down -v`.

## Ограничения проверки

Текущий демонстрационный стенд уже опубликован; подтверждённые проверки и оставшиеся
ограничения перечислены в [README.md](README.md). Для другого сервера их нужно повторить.
Реальный платёж ЮKassa, фискализация и длительная устойчивость под нагрузкой пока
не подтверждены. Подготовка конфигурации сама по себе не означает готовность принимать реальные заказы.
