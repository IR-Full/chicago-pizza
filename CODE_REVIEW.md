# Ревью кодовой базы Chicago Pizza

Дата: 16.09.2026. Разбор всего репозитория: `server/` (6 сервисов + 3 библиотеки), `client/`,
схема Prisma, docker compose, nginx, PWA. Ничего из перечисленного **не исправлено** — это план
работ.

Ссылки вида `файл:строка` указывают на состояние кода на момент ревью.

---

## 0. Общая картина

Что сделано хорошо и трогать не нужно:

- Деньги везде в копейках (`Int`), нигде нет `Float` для сумм.
- Цена считается только на сервере (`PricingService`), корзина хранит лишь конфигурацию —
  подделать сумму с клиента нельзя.
- Токены: refresh — случайная строка, в БД только SHA-256; есть детект повторного использования
  с отзывом всей «семьи» токенов.
- Пароли — bcrypt с настраиваемым числом раундов; коды и токены сброса тоже хранятся хешами.
- httpOnly-куки вместо токенов в JS; `Secure` выводится из схемы `CLIENT_URL`, а не из `NODE_ENV`
  (грабли, на которые обычно наступают).
- Нет ни одного `TODO`, `console.log` (кроме сид-скрипта) и ни одного `as any` в продакшн-коде.
- Тесты: 1096 на сервере (100% покрытие), 538 на клиенте (99% строк).

Ниже — 39 находок. Приоритеты: 🔴 чинить в первую очередь, 🟠 важно, 🟡 средне, ⚪ мелочь/вкусовщина.

## A. Функциональные баги

### 🔴 A1. Снятый с продажи товар «ломает» корзину целиком

`products/src/services/pricing.service.ts:42`, `orders/src/services/cart.service.ts:48-62`

`PricingService.priceOne` бросает `NotFoundException`, если товар не найден **или** `isActive=false`.
`CartService.getCart` прогоняет **все** строки корзины через этот метод одним RPC-вызовом. Значит:
достаточно, чтобы админ снял с продажи одну пиццу, лежащую у клиента в корзине (а корзина живёт в
Redis 7 дней) — и `GET /api/cart` начинает отдавать 404.

Последствия: счётчик в шапке показывает 0, страница корзины показывает «Корзина пуста», а
добавление нового товара падает с ошибкой (`addItem` в конце вызывает `getCart`). Пользователь не
может ни увидеть корзину, ни очистить её — состояние залипает на 7 дней.

Как чинить: `priceItems` должен возвращать по каждой строке результат вида
`{ ok: true, item } | { ok: false, reason: 'UNAVAILABLE', productId }`, а `getCart` — отбрасывать
недоступные строки, писать очищенный список обратно в Redis и возвращать их отдельным полем
`unavailable[]`, чтобы клиент показал «Пепперони больше нет в меню, мы убрали её из корзины».
`priceOne` продолжает бросать исключение только при прямом вызове из конструктора.

### 🔴 A2. «Повторить заказ» обещает пропускать недоступные товары, но не делает этого

`orders/src/services/order.service.ts:149-167`

Комментарий: *«skipping items no longer available»*. По факту фильтр один — `item.config !== null`.
Товары, снятые с продажи, попадают в корзину и приводят ровно к A1. Формулировка ошибки
«Нечего повторить: товары больше не доступны» тоже не соответствует условию — она срабатывает
только когда у всех позиций пустой `config`.

Как чинить: после A1 — переиспользовать тот же механизм: сложить строки, получить от products
список недоступных, положить в корзину только доступные, вернуть клиенту, сколько позиций
пропущено. Если доступных нет — `BadRequestException` с честным текстом.

### 🔴 A3. Отзывы о товарах никогда не появляются

`orders/src/services/order.service.ts:179-183`, `schema.prisma:359-372`,
`products/src/services/catalog.service.ts:71`

`Review` имеет опциональный `productId`, `CatalogService.getProduct` подтягивает `product.reviews`
(связь по `productId`). Но `submitReview` создаёт отзыв **без** `productId` — он всегда `null`.
Значит связь `Product.reviews` пуста всегда, карточка товара и блок отзывов на главной не
наполнятся ни при каких данных.

Дополнительно это концептуальная дыра: отзыв привязан к заказу, в заказе несколько разных товаров —
непонятно, к какому товару его относить.

Как чинить, два варианта:
1. **Отзыв о заказе** (проще): убрать `productId` из `Review`, показывать отзывы в истории заказов,
   а на главной/карточке — не показывать вовсе либо агрегировать по позициям заказа.
2. **Отзыв о товаре**: разрешить оценивать конкретные позиции доставленного заказа
   (`Review` → `@@unique([orderId, productId])`), тогда на карточке товара появляются настоящие
   отзывы, а рейтинг можно агрегировать в `Product`.

Пока не исправлено — раздел «Отзывы» на главной скрывается сам (он это умеет), но это костыль.

### 🟠 A4. Промокод можно использовать бесконечно одним и тем же аккаунтом

`orders/src/services/promocode.service.ts:19-41`, `order.service.ts:99`

Проверяются только `isActive`, `expiresAt`, общий `maxUses` и минимальная сумма. Нет ни истории
погашений, ни ограничения «один раз на пользователя». Классический промокод «−10% на первый заказ»
работает вечно для каждого клиента.

Как чинить: таблица `PromocodeRedemption { promocodeId, userId, orderId, createdAt,
@@unique([promocodeId, userId]) }` + поле `Promocode.perUserLimit Int @default(1)`; проверка и
вставка — внутри той же транзакции, что и создание заказа.

### 🟠 A5. Сообщения об ошибках на двух языках вперемешку

`auth/src/services/auth.service.ts` (английский) против `orders/`, `support/` (русский)

Клиент показывает `error.message` из API прямо в тосте. Пользователь на русском интерфейсе видит
«Invalid email or password» при входе и «Корзина пуста» при оформлении. Плюс сообщения валидации
дублируются на двух языках: `apps/auth/src/dto/register.dto.ts:27` (англ.) и
`apps/gateway/src/dto/auth.dto.ts:44` (рус.) — какое увидит пользователь, зависит от того, какая
валидация сработала первой.

Как чинить: сервер отдаёт машинный код (`code: 'INVALID_CREDENTIALS'`) + техническое сообщение для
логов, а человеческий текст берётся из словаря next-intl на клиенте. Минимальный вариант: привести
все сообщения к русскому и убрать дубли правил из DTO микросервисов.

### 🟡 A6. Цены и даты всегда форматируются по `ru-RU`, даже в английской версии

`client/src/shared/lib/format.ts:2,11,19`

Дефолт `locale = 'ru-RU'` зашит, ни один вызов локаль не передаёт. В EN-версии сайта цена и дата
рендерятся русским форматом.

Как чинить: брать локаль из `useLocale()` / `getLocale()` и передавать в хелперы, либо завести
`useFormatters()` поверх `useLocale`.

## B. Гонки и целостность данных

### 🔴 B1. Ротация refresh-токена не атомарна

`auth/src/services/token.service.ts:66-91`

Последовательность: `findUnique` → проверка `revokedAt === null` → `update`. Два параллельных
запроса с одним токеном (две вкладки, ретрай сети, переоткрытие приложения) оба пройдут проверку и
получат по новой паре. Детект повторного использования при этом **не** сработает — то есть защита,
ради которой всё и делалось, обходится гонкой.

Как чинить:
```ts
const { count } = await prisma.refreshToken.updateMany({
  where: { id: stored.id, revokedAt: null },
  data: { revokedAt: new Date() },
});
if (count === 0) { await this.revokeAllForUser(stored.userId); throw new UnauthorizedException(...); }
```

### 🟠 B2. Баллы лояльности можно потратить дважды

`orders/src/services/loyalty.service.ts:130-142`

Внутри транзакции: `findUniqueOrThrow` → `Math.min(points, user.loyaltyPoints, ...)` → `update
{ decrement }`. При уровне изоляции Read Committed (дефолт Postgres) два одновременных чекаута
прочитают одинаковый баланс и спишут его дважды — баланс уйдёт в минус.

Как чинить: условное списание
```ts
const { count } = await tx.user.updateMany({
  where: { id: userId, loyaltyPoints: { gte: usable } },
  data: { loyaltyPoints: { decrement: usable } },
});
if (count === 0) return 0; // баллы уже потрачены параллельным заказом
```

### 🟠 B3. `maxUses` промокода можно превысить

`orders/src/services/order.service.ts:56,99`

`promocodes.validate()` читает `usedCount` **до** транзакции, инкремент происходит внутри неё. Два
параллельных заказа с последним оставшимся использованием пройдут оба.

Как чинить: инкремент условным `updateMany({ where: { id, OR: [{ maxUses: null }, { usedCount: { lt: maxUses } }] } })`
с проверкой `count === 1`, иначе — откат транзакции с «промокод больше не действует».

### 🟡 B4. Начисление кешбэка не защищено от повторного перевода в DELIVERED

`orders/src/services/order.service.ts:208-231`, `loyalty.service.ts:36-54`

Переход в `DELIVERED` разрешён только из `ON_DELIVERY`, и статус пишется в той же транзакции —
на практике защищает. Но проверка допустимости перехода читает заказ **вне** транзакции
(`findUnique`, строка 209), так что два одновременных «доставлено» теоретически начислят баллы
дважды. Дёшево закрыть: `updateMany({ where: { id, status: 'ON_DELIVERY' } })` и проверка `count`.

## C. Безопасность

### 🟠 C1. Блокировка пользователя и смена роли действуют с задержкой до 15 минут

`auth/src/services/auth.service.ts:271-286`

`adminSetBlocked`/`adminSetRole` отзывают refresh-токены, но **выданный access-JWT продолжает
работать** до истечения `JWT_ACCESS_TTL`. Заблокированный пользователь спокойно оформляет заказы
ещё 15 минут; понижённый в правах админ 15 минут остаётся админом.

Как чинить: денилист в Redis — при блокировке/смене роли писать `revoked:user:<id> = timestamp`
(TTL = access TTL), гейтвей в `JwtAuthGuard`/`JwtStrategy` проверяет `payload.iat >= timestamp`.
Одно чтение Redis на запрос, зато мгновенный отзыв.

### 🟠 C2. Админские эндпоинты принимают неотвалидированное тело

`gateway/src/controllers/admin.controller.ts:74,81,90,132,138`

`createCategory`, `createProduct`, `updateProduct`, `setUserRole`, `setUserBlocked` типизированы
интерфейсами/`Prisma.*Input`, а не классами-DTO. `ValidationPipe` без метатипа-класса **пропускает
тело как есть** — `whitelist` ничего не отрезает. Тело уходит прямо в `prisma.product.create({ data })`.

Последствия: админ может записать произвольные поля (включая `id`, `createdAt`), а невалидная роль
даст 500 от Prisma вместо 400. Права админские, поэтому не критично, но это единственный
непровалидированный путь записи в проекте.

Как чинить: `CreateCategoryDto`, `CreateProductDto` (с `@ValidateNested` для `sizes[]`),
`UpdateProductDto`, `SetUserRoleDto` (`@IsEnum(Role)`), `SetUserBlockedDto` (`@IsBoolean`).

### 🟠 C3. Swagger открыт в проде

`gateway/src/main.ts:64-71`

`/api/docs` поднимается безусловно и не проходит через Nest-guard'ы (SwaggerModule вешает роут
мимо них). Публично отдаётся вся карта API и схемы DTO.

Как чинить: `if (process.env.NODE_ENV !== 'production')` либо basic-auth перед `SwaggerModule.setup`.

### 🟠 C4. CSP реально не применяется к страницам

`gateway/src/main.ts:26-40`, `infra/nginx/nginx.conf:20-25`

Helmet с аккуратно расписанным CSP стоит на гейтвее, то есть покрывает только JSON-ответы API.
HTML отдаёт Next.js через nginx, а там CSP нет вовсе. Заголовки, ради которых всё писалось, до
браузера в нужном контексте не доходят.

Как чинить: перенести CSP в nginx (`location /`) или в `next.config.mjs` → `headers()`. Учесть, что
Next в проде требует `'unsafe-inline'` для стилей и `'self'` для скриптов; если нужен строгий CSP —
nonce через middleware.

### 🟡 C5. HTTP-порт Postgres и UI RabbitMQ/MailHog опубликованы наружу

`docker-compose.yml:36-38,62-64,74-76`

`ports: 5432:5432` с дефолтным паролем `pizza` при `NODE_ENV: production`. Для локальной разработки
нормально, для развёртывания — прямой доступ к БД из интернета.

Как чинить: биндить на `127.0.0.1:5432:5432` или вынести публикацию портов в
`docker-compose.override.yml` для дева; MailHog в проде не поднимать вовсе.

### 🟡 C6. Админ может заблокировать сам себя / снять с себя роль

`auth/src/services/auth.service.ts:271-286`

Проверки «нельзя менять свою роль» и «нельзя удалить последнего админа» нет. Один неверный клик —
и в систему больше некому зайти (кроме ручного `UPDATE` в БД).

Как чинить: запрет `userId === currentUserId` для обеих операций + проверка, что остаётся хотя бы
один активный `ADMIN`.

## D. Производительность

### 🟠 D1. N+1 запросов при каждом чтении корзины

`products/src/services/pricing.service.ts:22-30`

`priceItems` идёт по строкам **последовательно**, каждый `priceOne` делает от 1 до 4 запросов
(товар, вторая половинка, тесто, ингредиенты). Корзина из 10 позиций — до 40 последовательных
round-trip'ов к Postgres. И это происходит:
- при каждом `GET /api/cart` (а `useCart()` вызывается в шапке, то есть **на каждой странице**),
- при каждом добавлении товара,
- при оформлении заказа.

Как чинить: предзагрузить всё пачкой перед циклом —
`product.findMany({ where: { id: { in: ids } } })`, `doughType.findMany`, `ingredient.findMany`, —
сложить в `Map` и считать цены в памяти. Один-три запроса вместо сорока.

### 🟠 D2. Главная страница не кешируется, хотя объявлена ISR-страницей

`client/src/app/page.tsx:13`, `client/src/shared/api/api-client.ts:70`

В `page.tsx` стоит `export const revalidate = 300`, но `apiRequest` по умолчанию проставляет
`cache: 'no-store'`. Любой `fetch` с `no-store` делает маршрут динамическим — в выводе `next build`
главная помечена `ƒ (Dynamic)`. ISR не работает: каждый заход рендерит страницу заново и бьёт в
гейтвей 2–5 раз (популярное, новинки и до трёх карточек товаров ради отзывов).

Как чинить: для публичного каталога не ставить `no-store`, а передавать
`next: { revalidate: 300 }`; приватные вызовы (`/auth/me`, `/cart`, `/orders`) оставить `no-store`.
Плюс — убрать отдельные запросы за отзывами (см. D3).

### 🟡 D3. Отзывы на главной стоят трёх дополнительных запросов

`client/src/app/page.tsx:16-25`

Чтобы собрать три цитаты, страница дёргает `productApi.get(slug)` для каждой популярной пиццы
(добавлено при редизайне). После исправления A3 правильнее завести один эндпоинт
`GET /api/reviews?limit=3` либо отдавать отзывы вместе со списком популярных товаров.

### 🟡 D4. Нет индекса на `products.categoryId` и других внешних ключах

`schema.prisma` — см. раздел E1. Фильтр меню по категории — самый частый запрос каталога.

### ⚪ D5. Поиск по названию/ингредиентам — `contains` без индекса

`products/src/services/catalog.service.ts:176-184`

`ILIKE '%x%'` по трём таблицам не использует индексы. На текущем объёме (десятки товаров) неважно,
но при росте меню — `pg_trgm` + GIN-индекс либо полнотекстовый поиск.

## E. Схема БД

### 🟠 E1. Отсутствуют индексы на внешних ключах

Prisma для Postgres **не создаёт** индексы под FK автоматически. Без индексов остались:

| Таблица | Колонка | Чем грозит |
|---|---|---|
| `products` | `categoryId` | фильтр меню по категории — seq scan |
| `orders` | `addressId`, `promocodeId`, `courierId` | удаление адреса/промокода блокируется полным сканом |
| `order_items` | `doughTypeId` | то же при удалении вида теста |
| `reviews` | `userId` | выборка отзывов пользователя |
| `loyalty_transactions` | `orderId` | связь начислений с заказом |
| `ticket_messages` | `senderId` | — |
| `notifications` | `(userId, createdAt)` | список сортируется по `createdAt`, индекс `(userId,isRead)` не помогает |

### 🟡 E2. `User.referredById` — колонка-призрак

`schema.prisma:41-42`

Поле объявлено как обычная строка (без `@relation(fields:)`), рядом `referredBy Referral?` — это
обратная связь на `Referral`, а не на пользователя. В итоге `referredById` записывается
(`auth.service.ts:74`), но не имеет ни внешнего ключа, ни индекса, и дублирует таблицу `Referral`.

Как чинить: либо полноценная self-relation с FK и индексом, либо удалить колонку и везде читать
`Referral`.

### 🟡 E3. Мёртвые поля схемы

- `User.failedLoginCount` — не используется нигде (throttling живёт в Redis).
- `Order.courierId` / `Order.courier` — курьер никогда не назначается; роль `COURIER` при этом видит
  **все** заказы со всеми телефонами и адресами.
- `Review.productId` — см. A3.
- `NotificationType.PROMO` / `SYSTEM` — не создаются никогда.

Как чинить: либо удалить миграцией, либо доделать (назначение курьера — осмысленная фича: курьер
должен видеть только свои заказы).

### 🟡 E4. Нет очистки протухших записей

Ни один процесс не удаляет истёкшие `refresh_tokens`, `email_verification_codes`,
`password_reset_tokens`, прочитанные `notifications`. Таблицы растут бесконечно.

Как чинить: cron-задача в сервисе auth (`@nestjs/schedule`) — раз в сутки удалять записи с
`expiresAt < now() - 30d`; индекс по `expiresAt` для этого же.

### ⚪ E5. `SupportTicket.updatedAt` выставляется вручную при `@updatedAt`

`support/src/services/support.service.ts:81`: `data: { updatedAt: new Date() }` — Prisma и так
обновит поле. Строка ничего не делает, но выглядит как значимая (и в тестах пришлось её описывать).
Заменить на «пустой» апдейт или убрать ветку.

### ⚪ E6. `OrderItem.productId` без FK

Осознанный снапшот (товар могут удалить) — но стоит написать это в комментарии рядом с полем, иначе
выглядит как забытая связь.

## F. Консистентность после редизайна

### 🟠 F1. PWA осталась в старой красной палитре

`client/public/manifest.webmanifest:11-12`, `client/public/offline.html:15-36`

`theme_color: "#c62828"`, `background_color: "#ffffff"`, кнопка на офлайн-странице `#c62828`,
фон `#fff` / `#171412`. Дизайн-система теперь кремовая `#f5ead8` с терракотой `#c67139`, а
`layout.tsx` отдаёт `themeColor: #f5ead8 / #1f1c19`. То есть цвет строки браузера и сплеш-экрана
установленного приложения не совпадают с самим приложением.

Как чинить: `theme_color: "#c67139"` (или `#f5ead8`), `background_color: "#f5ead8"`, офлайн-страницу
перекрасить в токены Organic и поставить Nunito с системным фолбэком.

### 🟡 F2. Иконки PWA не перерисованы

`client/public/icons/icon-192.png` (547 байт) и `icon-512.png` — судя по размеру, плейсхолдеры со
старым логотипом. На плитке приложения будет не тот знак, что в шапке сайта.

### 🟡 F3. Версия кеша service worker'а зафиксирована строкой

`client/public/sw.js:11` — `CACHE_VERSION = 'chicago-pizza-v1'` не меняется между сборками, поэтому
`offline.html` и `manifest.webmanifest` в кеше пользователя не обновятся никогда (пока строку не
поменять руками). После F1 это особенно неприятно: старая красная офлайн-страница останется у всех,
кто уже заходил.

Как чинить: подставлять `BUILD_ID` при сборке либо кешировать эти два файла стратегией
network-first.

## G. Функциональные пробелы

### 🟠 G1. Пагинации нет нигде, кроме API

- `client/src/app/orders/page.tsx:23` — `useOrders(1)`, видно только 20 последних заказов, старые
  недостижимы.
- `admin/page.tsx`, `admin/users/page.tsx`, `admin/tickets/page.tsx` — всегда страница 1. Кухня
  видит 20 последних заказов; при потоке заказов старые уезжают из интерфейса совсем.
- `widgets/catalog/catalog-view.tsx` — `limit: 60` без «показать ещё».

Бэкенд пагинацию поддерживает везде — не хватает только UI.

### 🟡 G2. Уведомления пишутся в БД, но их никто не показывает

`notifications` создаются на каждую смену статуса и ответ поддержки, есть эндпоинты списка и
«прочитано», на клиенте есть хук `useNotifications` и метод `supportApi.markRead` — и **ни одной
точки использования**. Данные копятся, пользователь их не видит.

Как чинить: колокольчик в шапке со счётчиком непрочитанных + сокет-событие
`WS_EVENTS.NOTIFICATION` (константа объявлена на обеих сторонах, но никем не отправляется). Либо
честно удалить неиспользуемый слой.

### 🟡 G3. Доставка «ко времени» не проверяется против часов работы

`orders/src/services/order.service.ts:41-46` — проверяется только «не раньше чем через 30 минут».
Заказ можно запланировать на 04:00, хотя пиццерия работает 10:00–23:00 (это написано в подвале и в
контактах).

Как чинить: константы часов работы в конфиг + валидация окна доставки (и заодно предупреждение на
клиенте в `datetime-local`).

### ⚪ G4. Неизвестный query-параметр ломает запрос к API

`gateway/src/main.ts:48-54` — `forbidNonWhitelisted: true` применяется и к `@Query()`. Запрос
`GET /api/products?utm_source=vk` вернёт 400 «property utm_source should not exist». Клиент такие
ссылки не строит, но любая внешняя интеграция или ручной запрос об это споткнётся.

Как чинить: для query-DTO отдельный pipe без `forbidNonWhitelisted` (whitelist-отрезание достаточно).

## H. Дублирование и мёртвый код

### 🟡 H1. `libs/common` экспортирует хелперы, которыми никто не пользуется

| Экспорт | Статус |
|---|---|

Как чинить: либо применить (наиболее полезно — `paginate()` и `WsJwtGuard`), либо удалить, чтобы
библиотека не выглядела богаче, чем есть.

### 🟡 H2. Порог бесплатной доставки и её стоимость заданы в четырёх местах

`orders/src/services/order.service.ts:10-11`, `client/src/app/cart/page.tsx:16-17`,
`client/src/app/checkout/page.tsx:24-25`, плюс текстом в словарях
(`home.promos.delivery.body`, `footer.deliveryPrice`).

Изменение тарифа потребует правок в четырёх файлах, и расхождение между текстом и расчётом
пользователь заметит сразу.

Как чинить: отдавать тариф с сервера (`GET /api/delivery-terms` или полем в ответе корзины),
подставлять числа в переводы через `t('...', { fee, threshold })`.

### 🟡 H3. Правила пароля и телефона продублированы трижды

`apps/auth/src/dto/register.dto.ts`, `apps/gateway/src/dto/auth.dto.ts`,
`client/src/features/auth/model/schemas.ts` — три копии одного регэкспа. Уже разошлись по языку
сообщений (см. A5).

Как чинить: вынести регулярки и границы длин в `libs/common` (сервер) и импортировать одну
константу; на клиенте держать зеркало с комментарием «синхронизировать с libs/common».

### ⚪ H4. `PromocodeService.incrementUsage` не вызывается

`orders/src/services/promocode.service.ts:44-49` — инкремент сделан инлайном в `checkout`.
Метод-сирота, дублирующий логику. Удалить либо использовать (и тогда сразу с условием из B3).

### ⚪ H5. Спеки попадают в Docker-образ

`.dockerignore` (обе стороны) не исключает `**/*.spec.ts`. В `dist` их больше нет, но исходники
копируются в runtime-слой (`COPY --from=builder /app ./`). Лишний вес и лишняя поверхность.

## I. Эксплуатация и инфраструктура

### 🟠 I1. Нет graceful shutdown ни в одном сервисе

`enableShutdownHooks()` не вызывается нигде (`apps/*/src/main.ts`). Следствия: `PrismaService.
onModuleDestroy` не отрабатывает, соединения с Postgres/Redis/RabbitMQ рвутся по SIGKILL,
незавершённые HTTP-запросы обрываются при деплое.

Как чинить: `app.enableShutdownHooks()` + для гейтвея закрывать Redis-клиенты адаптера сокетов.

### 🟠 I2. `noAck: true` — события теряются при падении обработчика

`libs/rabbitmq/src/rabbitmq.options.ts:15`

Сообщение подтверждается в момент доставки. Если обработчик `@EventPattern` упал (SMTP недоступен,
процесс перезапустился) — письмо о заказе не уйдёт никогда, и следов не останется. Для
request/response это приемлемо, для событий — нет.

Как чинить: `noAck: false` и ручной ack после успешного выполнения, либо оставить как есть, но
завести отдельную очередь для событий с ack + dead-letter.

### 🟠 I3. У пяти микросервисов нет healthcheck

В `docker-compose.yml` healthcheck объявлен только для `gateway`. Остальные пять — чистые
RMQ-микросервисы без HTTP-порта, поэтому проверить их нечем: зависший потребитель остаётся «up».

Как чинить: поднимать в каждом сервисе гибридное приложение (`app.connectMicroservice` +
`app.listen(PORT)`) с `HealthModule`, либо healthcheck-скриптом проверять наличие потребителя в
очереди через RabbitMQ API.

### 🟡 I4. Грабли сборки: `deleteOutDir` + `tsconfig.tsbuildinfo`

Обнаружено при подготовке тестов и уже исправлено (`incremental: false` у приложений), но стоит
зафиксировать: `nest build` сначала удаляет `dist`, а `tsc` с залипшим `tsbuildinfo` считает, что
собирать нечего — на выходе **пустой `dist` и код возврата 0**. Если кто-то вернёт `incremental`,
грабли вернутся. Стоит добавить в CI шаг «после сборки проверить, что `dist/main.js` существует».

### 🟡 I5. `seed.js` выполняется при каждом `docker compose up`

`docker-compose.yml:80-88` — сервис `migrate` гоняет `prisma migrate deploy && node seed.js`.
Сид на upsert'ах, то есть идемпотентен, но он **перезапишет цены**, изменённые админом через панель,
при следующем рестарте стека.

Как чинить: сид только по флагу (`SEED_ON_START=true`, по умолчанию выключен в проде) или
проверка «в базе уже есть товары — выходим».
